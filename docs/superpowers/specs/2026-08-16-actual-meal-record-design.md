# 实际辅食记录设计

## Objective

在不覆盖计划菜单的前提下，允许用户为任一计划餐次记录宝宝实际吃了什么。实际记录应能在当前菜单和历史菜单中查看，并能安全地新增、修改或删除。

## Scope

每个菜单餐次最多保存一份 `actualMeal`：

- `name`：实际菜名，必填，去除首尾空白后不能为空。
- `occurredAt`：实际进食时间，必填，必须是有效时间。
- `amount`：食量，自由文本，可选，例如“半碗”或“80克”。
- `note`：备注，自由文本，可选。
- `createdAt`：首次保存时间。
- `updatedAt`：最近修改时间。

实际记录属于对应菜单餐次，不替换计划菜谱或 `recipeId`。本阶段不增加营养计算、食材拆分、独立趋势统计或一餐多条实际记录。

## User Experience

### 新增

- 没有实际记录的餐次显示“记录实际吃了”。
- 表单包含实际菜名、实际进食时间、食量和备注。
- 当天餐次默认当前时间；历史餐次默认使用该餐次日期，并提供可编辑的日期时间控件。
- 表单提供“同时把原计划标记为已吃”复选框，由用户每次决定，不强制默认联动。

### 展示

计划菜名和状态继续保留。
- 计划内容下方显示独立的“实际吃了”摘要，包括菜名、时间、食量和备注；空的可选字段不显示占位噪音。
- 动态文本必须转义，时间使用本地可读格式。

### 修改和删除

- 有实际记录时，“记录实际吃了”变为“修改实际记录”，并提供删除入口。
- 当前 7 天菜单可以直接操作。
- 历史菜单默认只读；只有用户先点“修改记录”解锁当前选中的历史菜单后，才能新增、修改或删除实际记录。
- 删除仅删除 `actualMeal`，不改变计划菜谱或餐次状态。

## Data Model and Persistence

`actualMeal` 作为 meal 的可选嵌套对象，跟随 `weeklyMenus` 保存。这样无需新增 IndexedDB store 或数据库版本，并复用现有按菜单 ID 串行、事务内读取最新记录、原子写回的菜单变更边界。

新增、修改、删除都必须：

1. 在操作入口捕获宝宝 ID、菜单 ID 和餐次 ID。
2. 在事务内重新读取最新菜单。
3. 校验菜单仍属于目标宝宝、餐次仍存在。
4. 基于最新记录写回，避免并发状态或其他餐次修改丢失。
5. 保存失败时不修改 Store 快照，恢复按钮并显示错误。

当用户勾选“同时把原计划标记为已吃”时，`actualMeal` 与餐次 `status: "eaten"` 必须在同一次菜单写入中完成。未勾选时保持原状态不变。

## Compatibility and Backup

- 缺少 `actualMeal` 的现有菜单保持兼容并正常显示。
- V1 备份继续使用当前 schema 版本；导出会自然包含嵌套字段。
- 导入校验允许缺少 `actualMeal`，但存在时必须校验其对象结构、必填字段和时间有效性。
- 未知或畸形的 `actualMeal` 不得导致原生类型错误；导入应统一报告 `weeklyMenus` 字段无效。
- 不改写或虚构旧菜单的实际进食记录。

## Error Handling and Safety

- 菜名为空、时间无效时在提交前提示，不能写入。
- 菜单或餐次已被删除、宝宝已切换时拒绝写入，不能重建陈旧数据。
- 删除前显示明确确认，取消后不产生写入。
- 操作进行期间锁定同一菜单的相关控件，完成或失败后恢复。

## Mobile and Accessibility

- 表单使用带标签的原生输入控件；日期时间控件使用 `datetime-local`。
- 保存、取消和删除按钮保持至少 44px 触控高度，并在 320px 宽度下换行而不产生页面级横向滚动。
- 实际记录摘要使用明确标题，不仅依赖颜色区分计划与实际内容。
- 只读历史菜单不渲染可操作按钮。

## Verification

自动测试至少覆盖：

- 新增实际记录，计划菜谱保持不变。
- 未勾选时餐次状态保持不变；勾选时同一写入变为 `eaten`。
- 修改保留 `createdAt` 并刷新 `updatedAt`。
- 删除只移除 `actualMeal`。
- 当前菜单可操作、历史菜单锁定和解锁边界。
- 并发菜单更新不会覆盖其他餐次或其他已提交字段。
- 菜单/餐次删除、宝宝切换和写入失败不会复活或污染数据。
- 旧菜单和旧 V1 备份继续通过；合法新备份可恢复；畸形嵌套字段被拒绝。
- 动态文本转义、表单标签、44px 控件和 320px 布局契约。

浏览器验收至少验证一次当前菜单新增、历史菜单修改、可选“已吃”联动、删除确认及 iPhone 宽度布局。

## Rollback

代码回滚后，旧客户端会忽略 meal 上未知的 `actualMeal` 字段，计划菜单仍可使用。若需要重新发布旧版本，只需回退功能提交并提升 Service Worker 缓存版本；无需迁移或删除数据库记录。
