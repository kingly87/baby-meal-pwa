# 早餐菜单、菜单历史与每日具体数值设计

日期：2026-08-15

## Objective

在不破坏现有宝宝资料、菜单、记录和备份的前提下：

1. 将周菜单从每天两餐扩展为早餐、午餐、晚餐三餐。
2. 让用户可以查看以前保存的周菜单，并在明确确认后纠正历史菜单。
3. 在生活趋势图上直接显示每天的睡眠、奶量、便便和尿尿具体数值。

本期不扩充食谱总量，也不重写现有重复食谱；菜谱去重分组和新增独立食谱留到下一版。

## Constraints

- 应用继续保持纯前端、本地优先 PWA，不增加服务器或账号系统。
- 数据继续保存在当前浏览器的 IndexedDB，并包含在 JSON 备份中。
- 排除食材和宝宝辅食阶段始终是菜单生成的硬性限制。
- 现有旧菜单必须可以读取，不能要求用户重新创建宝宝或重新导入数据。
- iPhone 小屏幕上不能因 14 天或 30 天数据造成数字重叠。
- 用户已有的 `README.md` 和 `AGENTS.md` 工作区改动不属于本功能范围。

## Current State

- 当前周菜单每天生成两餐，餐次仅以数组位置表示，没有稳定的餐次字段。
- 每次生成菜单都会写入一条新的 `weeklyMenus` 记录；旧记录仍在 IndexedDB 和备份中，但界面只显示按 `startDate` 排序后的最新一条。
- 当前菜单支持“换一道、已吃、跳过”，不支持在界面查看或编辑历史周菜单。
- 食谱数据已经包含部分带有 `mealSlots: ['早餐', ...]` 的食谱，可供本期早餐生成使用。
- 生活趋势已经支持睡眠、奶量、便便、尿尿以及 7/14/30 天范围，但页面重点只呈现平均值，单日值不够直观。

## User Experience

### 周菜单

- 每天固定显示三餐：早餐、午餐、晚餐。
- 每道菜前明确显示餐次名称。
- 早餐只从 `mealSlots` 包含“早餐”的安全候选中生成。
- 午餐和晚餐从包含对应正餐餐次的候选中生成；旧食谱缺少餐次元数据时，作为午餐或晚餐兼容候选，不作为早餐候选。
- 同一天尽量避免重复蛋白质类别、主食形态和烹饪方式。
- 如果当前阶段和排除条件下没有安全早餐候选，显示明确错误，不用不合适的食谱代替。

### 历史菜单

- 菜单页增加“本周菜单 / 历史菜单”切换。
- 历史菜单按开始日期倒序显示日期范围，例如“8月10日—8月16日”。
- 当前周直接提供“换一道、已吃、跳过”。
- 历史周默认只读。点击“修改记录”后，弹出“正在修改过去的饮食记录”确认提示；确认后才开放换菜和状态修改。
- 历史修改保存到原菜单记录，不复制出另一份记录。
- 重新生成当前周前弹出确认；确认后替换同一宝宝、同一周的菜单，避免积累多份无法区分的同周记录。

### 每日具体数值

- 保留现有平均值和周期对比。
- 每根柱子顶部直接显示当天具体值，无需点击：
  - 睡眠：小时，例如 `11.3`
  - 奶量：毫升，例如 `680`
  - 便便、尿尿：次数，例如 `3`
- 柱子下方显示日期，例如 `8/15`。
- 7 天完整显示在一屏；14 天和 30 天使用横向滚动，保证每根柱子和数值可读。
- 当天没有任何记录时显示 `—`；真实记录值为零时显示 `0`，两者不可混淆。
- 用户可继续切换睡眠、奶量、便便、尿尿以及 7/14/30 天。
- 新增、修改或删除日常记录或睡眠记录后，图表在现有刷新周期中立即更新。

## Data Model and Compatibility

### New meal field

新生成的每个 meal 增加稳定字段：

```js
mealType: 'breakfast' | 'lunch' | 'dinner'
```

`slot` 可继续保留用于旧逻辑兼容，但界面和新逻辑以 `mealType` 为准。

### Legacy menu interpretation

- 旧菜单没有 `mealType` 时不回写、不批量迁移。
- 旧菜单第 1 餐解释为午餐，第 2 餐解释为晚餐。
- 如果旧菜单存在第 3 餐，则依次解释为早餐、午餐、晚餐，仅用于显示兼容。
- 导出备份保留原记录；新修改过的菜单会自然写入 `mealType`。

### Week identity

- 当前周按本地时间的周一至周日计算，以 `babyId + normalizedWeekStart` 唯一识别。
- 生成菜单时先查找同一宝宝、同一周记录；用户确认后更新该记录，而不是新增重复周。
- 其他周和其他宝宝的数据不受影响。

## Components

### Meal planner

- 接受明确餐次序列，而不是只接收餐数。
- 为每个餐次建立候选池，并沿用阶段、排除、收藏和不喜欢权重。
- 早餐候选严格验证 `mealSlots`。
- 多样性规则在同一天三餐之间工作，并在候选不足时记录已放宽的软规则；硬性安全规则永不放宽。

### Menu history state

- 应用状态保存当前查看的周菜单 ID 和历史编辑授权状态。
- 切换宝宝、导入备份或删除宝宝时重置菜单历史选择。
- 所有换菜和状态操作都携带目标周菜单 ID，不能默认修改 `store.week`。

### Menu UI

- 提供当前周与历史菜单入口、周范围标题、餐次标签和历史编辑确认入口。
- 历史菜单处于只读状态时隐藏或禁用修改按钮，并给出清晰说明。

### Daily trends UI

- 在现有趋势模型上消费每个 `point` 的日期、值和是否缺失状态。
- 柱状图为每个点渲染数值标签和日期标签。
- 14/30 天容器允许横向滚动，并保持触控滚动和可访问文本。

## Data Flow

1. 页面刷新时读取当前宝宝的全部 `weeklyMenus`，按周分组并选出当前周。
2. 用户生成菜单时，规划器按早餐、午餐、晚餐建立安全候选并产生 21 餐。
3. 如果当前周已存在菜单，先确认，再原位替换；否则新建当前周记录。
4. 用户进入历史菜单时选择目标周；历史菜单保持只读，直到确认进入修改状态。
5. 修改操作使用目标菜单 ID 写回对应记录，然后刷新该周显示。
6. 趋势页面继续从当前宝宝的日常记录和睡眠记录计算点位，UI 直接呈现每个点的值。

## Error Handling

- 无安全早餐候选：停止整周生成并说明是阶段或排除条件导致，不保存半份菜单。
- 当前周替换写入失败：保留旧菜单并显示错误。
- 找不到历史菜单或菜单已被删除：退出历史编辑并返回当前周。
- 历史修改未经确认：拒绝写入。
- 单个趋势日期缺失：显示 `—`，不把缺失数据算作零。
- IndexedDB 读取失败：沿用现有“数据暂时无法读取”状态，不显示误导性零值。

## Verification

自动化测试至少覆盖：

- 每周生成 7 天、每天早餐/午餐/晚餐，共 21 餐。
- 早餐只使用允许早餐的食谱，并继续遵守阶段和排除食材。
- 午餐和晚餐不会误用仅限早餐的食谱。
- 同一天优先轮换蛋白质、主食形态和烹饪方式。
- 旧两餐菜单解释为午餐和晚餐，且读取过程不修改原对象。
- 同一周重新生成会更新原记录，不产生重复周。
- 历史菜单默认只读，确认后才能修改指定历史周。
- 切换宝宝、导入和删除宝宝后重置历史菜单状态。
- 7/14/30 天的每个柱子都有具体值和日期；缺失显示 `—`，真实零显示 `0`。
- 奶量、睡眠、便便、尿尿切换后使用正确单位。
- JSON 备份可以导出和恢复包含 `mealType` 的新菜单，同时继续接受合法旧菜单。

还需进行手机宽度浏览器验证：当前周三餐、历史确认编辑、7 天一屏、14/30 天横向滚动，以及 iPhone 中文和触控交互不受影响。

## Rollback

- 本功能使用独立提交，可通过回退该提交恢复旧界面和生成逻辑。
- 新增的 `mealType` 是向后兼容字段，旧代码会忽略它，因此代码回退不会损坏菜单。
- 不执行批量数据迁移；旧菜单保持原样，降低回滚风险。
- 同周覆盖前由用户确认；写入使用完整菜单记录，失败时不删除原菜单。
